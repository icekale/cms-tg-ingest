# Web 任务终止与删除设计

## 背景

新 Vue Web UI 的任务列表目前只能查看任务。用户需要在列表中终止不应继续执行的任务，并删除已经结束的本地任务记录。

任务执行由 TaskStore 和 TaskRunner 协作完成。Runner 通过 claim 独占一个阶段，而阶段内部可能已经发出 CMS 或 115 请求。因此，终止不能直接删除任务或强制释放 claim，否则远端调用仍可能完成，但本地已经失去状态和审计记录。

## 目标

- 在新 Vue 任务列表中提供独立的“终止”和“删除”操作。
- 排队任务可以立即终止，运行中任务在当前阶段调用结束后停止。
- 终止后保留阶段、事件、错误和操作记录。
- 只允许永久删除已经结束且没有活动 claim 的本地任务。
- 用事务和条件更新处理 Web 操作与 Runner 并发执行的竞态。

## 非目标

- 不取消已经发出的 CMS、115 或 Emby 请求。
- 不删除 115 文件、分享、STRM 文件或 Emby 媒体。
- 不给 Telegram Bot 或旧 Web 页面增加按钮。
- 不提供批量终止或批量删除。
- 不强制中断 Python 线程。

## 状态模型

新增 `TaskStatus.CANCELLED = "cancelled"`。任务被终止后保留原 `current_stage`，以便界面和事件时间线说明任务停在哪个阶段。

终止分为两个状态：

1. **终止已请求**：任务仍被 Runner claim，`status` 暂时保持 `running`，元数据记录终止请求。
2. **已终止**：Runner 已在安全边界确认请求，或任务在请求时没有 claim，`status` 变为 `cancelled`，claim 被清除，任务不再可调度。

元数据使用以下字段：

- `termination_requested_at`：终止请求时间戳；大于零表示请求尚待 Runner 确认。
- `termination_requested_by`：请求来源，本功能写入 `Web`。

任务进入 `cancelled` 后清除上述待确认字段，并写入终止事件。`cancelled` 是终态，不进入 `claim_next_runnable`，不计入运行、失败或待人工处理任务。

## 后端操作

### 请求终止

TaskStore 增加原子化的终止请求方法。该方法在一个事务中读取并更新任务：

- 任务不存在：返回不存在。
- 已是 `cancelled`：幂等返回当前任务。
- 已是 `succeeded`、`failed` 或 `needs_action`：拒绝终止，提示任务已经结束。
- 无活动 claim 的 `pending` 或 `running` 任务：立即设为 `cancelled`，将 `next_run_at` 设为 `-1`，写入“Web 已终止任务”事件。
- 有活动 claim 的任务：保持当前状态和 claim，只合并终止请求元数据，并写入“Web 已请求终止，等待当前阶段结束”事件。
- 已存在终止请求：幂等返回当前任务，不重复写入请求事件。

请求操作不能覆盖当前阶段、错误信息或已有元数据。

### Runner 确认终止

TaskStore 增加按 `task_id + claimed_by + claim_token` 确认终止的方法。只有 claim 仍属于当前 Runner 且元数据存在终止请求时，才执行以下原子更新：

- 状态改为 `cancelled`。
- 保留当前阶段和已有错误信息。
- 清除 claim、claim heartbeat 和待确认终止元数据。
- 将 `next_run_at` 设为 `-1`。
- 写入“任务已终止，不再执行后续阶段”事件。

TaskRunner 在以下安全边界调用该方法：

1. 取得 claim 后、执行锁和业务阶段前。
2. 准备好全局锁后、调用 `workflow.run_stage` 前。
3. `workflow.run_stage` 返回后、应用阶段结果前。
4. 阶段抛出异常后、记录失败前；若此时存在终止请求，终止事件同时记录该异常摘要和详情，不再把任务转为 `failed`。

如果终止请求恰好发生在检查与阶段结果提交之间，TaskStore 的事件更新必须保留终止元数据。任务进入下一阶段后会再次被 claim，并在执行任何新副作用前终止。

正在进行的 CMS、115 或 Emby 调用不会被撤回。界面确认文案和事件记录必须明确说明这一限制。

### 安全删除

TaskStore 增加单任务删除方法，并在一个事务中检查和删除：

- 仅允许状态为 `succeeded`、`failed`、`needs_action` 或 `cancelled` 的任务。
- 无论状态如何，只要存在活动 claim 就拒绝删除。
- 依次删除该任务的 `task_events`、`task_operations` 和 `tasks` 记录。
- 不执行任何远端调用或文件操作。

删除不存在的任务返回不存在；状态不允许或存在 claim 时返回冲突。现有“清除历史”应把 `cancelled` 视为可清理终态，但保持其原有其他状态策略不变。

## API 设计

### 终止任务

`POST /api/v1/tasks/{id}/actions/terminate`

- `200`：终止已完成、终止请求已登记，或任务此前已终止。
- `404`：任务不存在。
- `409`：任务已经以其他终态结束，或状态在操作期间发生不兼容变化。

响应继续使用序列化后的任务对象。

### 删除任务

`DELETE /api/v1/tasks/{id}`

- `200`：返回被删除的任务 ID 和确认信息。
- `404`：任务不存在。
- `409`：任务仍活动、仍有 claim，或状态在操作期间发生变化。

### 可用操作

任务列表和详情响应增加：

- `available_actions`：后端根据实时快照返回操作名。
- `termination_requested`：当前是否正在等待 Runner 确认终止。

规则如下：

- 活动且未请求终止：包含 `terminate`，即使任务当前有 claim。
- 已请求终止：不再包含 `terminate`。
- 允许安全删除且无 claim：包含 `delete`。

前端只呈现后端返回的操作，不自行复制状态判断规则。

## Web UI

`frontend/src/views/Tasks.vue` 增加“操作”列：

- `terminate` 可用时显示警告样式的“终止”按钮。
- `delete` 可用时显示红色“删除”按钮。
- `termination_requested` 为真时显示“终止处理中”，不允许重复提交。
- 每个任务维护独立 loading 状态，避免一个操作阻塞整张表或被重复点击。

两个操作都使用 Naive UI 确认弹窗：

- 终止确认说明当前远端调用可能已经发生，只会阻止后续阶段。
- 删除确认说明将永久删除本地任务、时间线和操作记录，但不会删除媒体或网盘内容。

操作成功后重新加载任务列表并显示成功消息。API 返回 `404` 或 `409` 时保留当前行、显示具体原因并刷新列表，以呈现最新状态。

状态 `cancelled` 在 UI 显示为“已终止”。其他状态标签和任务详情路由保持不变。

## 兼容性与安全性

- SQLite 的状态列是文本，不需要数据库结构迁移。
- 所有新增写操作都通过 TaskStore 事务执行，不在 Web API 中直接拼接更新语句。
- Runner 只接受匹配的 claim token 来确认终止，过期 Worker 不能终止已被新 Worker 接管的任务。
- 删除操作不复用批量清理的先查后删流程，避免检查后状态发生变化。
- 任务事件保留终止请求与最终终止两个时间点，便于诊断远端副作用是否发生。

## 测试与验收

### TaskStore

- 排队任务请求终止后立即进入 `cancelled`，且不能再次 claim。
- 已 claim 的任务只登记终止请求，不清除 claim。
- 匹配 claim token 的 Runner 能确认终止；错误或过期 token 不能确认。
- 重复请求终止不重复写事件。
- 终态任务拒绝终止，已终止任务幂等成功。
- 仅允许删除无 claim 的终态任务，并同时删除事件和操作记录。
- 活动任务、活动 claim 和并发状态变化均拒绝删除。

### TaskRunner

- claim 前后出现终止请求时，不调用下一阶段工作流。
- 阶段执行期间出现终止请求时，阶段返回后不应用正常结果。
- 阶段异常与终止请求同时出现时，以已终止收口并保留可诊断事件。
- 检查后发生的竞态会在下一阶段执行前停止，不产生额外阶段副作用。

### Web API 与前端

- API 覆盖 `200`、`404` 和 `409` 响应。
- 序列化任务返回准确的 `available_actions` 和 `termination_requested`。
- 列表正确显示终止、终止处理中、删除三种操作状态。
- 确认、逐行 loading、成功刷新和错误提示正常工作。
- 执行现有 Python 测试、前端单元测试和前端生产构建，确认无回归。

## 验收标准

1. 用户可以从新 Web UI 任务列表终止排队或运行中的任务。
2. 终止请求不会强制释放正在执行的 claim，也不会让任务进入后续阶段。
3. 用户只能删除已结束且无 claim 的本地任务记录。
4. 所有操作都有确认、明确反馈和可追溯事件。
5. 现有 CMS、115、STRM、Emby、TG 和旧 Web 工作流行为不变。
