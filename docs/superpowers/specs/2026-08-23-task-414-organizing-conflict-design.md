# 任务 414 整理目录冲突修复设计

## 背景

任务 414 的 30 个接收文件已经被 CMS 整理完成，但分别进入两个不同的 TMDB 目录（S01 和 S02）。任务长期停留在 `organizing`，原因是整理目录解析器在发现第一个目录只包含部分文件后立即返回 `INCOMPLETE`，没有继续收集剩余文件，因此没有触发已有的多目录冲突保护。

## 目标

- 目录解析必须汇总本轮已发现的全部接收文件，再判断唯一目录、目录冲突或仍未完成。
- 任务文件落入多个媒体目录时，进入已有的 `NEEDS_ACTION` 安全分支，而不是继续自动重试。
- 保持单目录、文件尚未出现、接收目录残留等既有行为不变。
- 任务 414 在远端数据库中安全转为人工处理，不重复接收、创建分享或删除源文件。

## 方案

修改 `app/workflows/self_share.py::_resolve_intake_dest_folder`：

1. 每次按文件名或文件 ID搜索后，继续将命中的文件和父目录加入累计集合。
2. 不在发现首个部分目录时立即返回 `INCOMPLETE`；只有在全部候选文件已处理后，统一调用 `dest_id_from_file_hits`。
3. 若最终得到多个目录，返回现有 `CONFLICT`；调用方已经将其转换为“接收文件落到多个片库目录，已停止自动绑定”。
4. 若只有一个目录但未包含全部文件，继续返回 `INCOMPLETE`。

不放宽多目录绑定，不新增任务拆分逻辑，避免影响自有分享、STRM 移动和源清理语义。

## 测试

新增回归测试：构造两个不同季目录，各自包含同一任务的一部分接收文件，验证整理解析返回冲突；同时保留单目录部分命中继续等待的断言。先运行失败测试，再实施最小修复，最后运行相关测试和完整测试集。

## 远端处置

代码验证通过并发布到远端容器后，重新检查任务 414。若任务仍处于 `organizing`，只通过已有人工动作/TaskStore 状态保护将其置为 `NEEDS_ACTION`，保留事件和错误原因；不直接删除任务、不删除 115 文件。
